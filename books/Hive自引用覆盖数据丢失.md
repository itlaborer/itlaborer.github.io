# 一条自引用 SQL，把整张表冲掉了

## 事故长什么样

> 目标表被覆盖成只剩一个分支的残片，另一半数据和原有底稿一起没了。

一条自引用的覆盖语句跑完，目标表里的数据被冲掉了大半。

影响的记录数和业务时段还在核对【需补充】。现场能看到的直接结果是：表目录下留着 union 的子目录，本该被合并进来的另一个分支没影了，原表数据也不见了。查这张表还能查到东西，但查到的只是本该写进去的一半。

这类事最容易在四种情况下踩到：任务被人为杀掉、失败后重试、同一个调度被并发跑了两次，还有自引用本身把提交路径搞乱。当天具体是哪一种，得翻 yarn application 日志和调度记录才能定【需补充】。但不管哪种，结果都一样——提交没走完，表目录已经被切走了。

## 先看这条 SQL 在干什么

表名脱敏之后，原语句的结构是这样：

```sql
INSERT OVERWRITE TABLE db.T
SELECT <30 个字段>
FROM   db.T
WHERE  concat(uuid,DJXH) NOT IN (
           SELECT concat(uuid,DJXH)
           FROM   db.T_ZL
           WHERE  CZLX IN ('U','D')
       )
UNION ALL
SELECT <30 个字段>
FROM   db.T_ZL
WHERE  CZLX IN ('I','U');
```

典型的 CDC 合并。第一个分支从目标表里剔除被增量表标成更新或删除的旧记录，第二个分支把增量表里新增和更新后的新值捞出来，拼一起覆盖回目标表。

逻辑本身没问题。问题出在最后那一步——读的是它，写的也是它。

## 根子在提交阶段，不在 SELECT

Hive 跑这条 SQL 的时候，两个 union 分支不是直接往目标表写。它们各自写到临时目录，类似 `_task_tmp.HIVE_UNION_SUBDIR_1` 和 `HIVE_UNION_SUBDIR_2`。等两个分支都跑完，才由 MoveTask 统一搬运、合并、替换表目录。

这个提交动作是有窗口的。窗口里一旦断掉，就可能出现一个子目录已经搬进表目录、另一个还留在 staging 里，而外层覆盖已经生效。Hive 不会回滚，它只认最后表目录里剩了什么。

自引用把后果又放大了一层。普通的 INSERT OVERWRITE 失败，最坏是目标表空了，至少源表还在，重跑一次能补回来。这里源表就是目标表自己，原始数据跟着覆盖一起没了，重跑只会把残片再复制一遍。

所以这不是偶尔不安全。是出事之后连重跑补数据的余地都没有。

## 我一开始只想着拆自引用

第一版改法很直接：把读目标表的那个分支先写成中间表，覆盖语句里不再出现目标表名。

改完又想了一遍，发现没改干净。覆盖语句里还留着 UNION ALL——两个分支照样各写各的 staging 子目录，照样要走 MoveTask 合并。自引用是去掉了，提交阶段的窗口还在。这时候再断一次，丢的只是另一半增量，不至于连底稿都没了，可数据还是缺的。

要彻底绕开，得把 UNION 也一起物化。最后的覆盖语句里，只能有一个数据源。

## 改写后的四步

第一步，把目标表当前的快照落到中间表。原 SQL 里读目标表的逻辑原封不动搬过来，包括那个 NOT IN 子查询。这一步必须在覆盖之前做，读到的才是恢复后的完整数据。

第二步，把增量表里有效的部分落到第二张中间表，也就是 CZLX 在 I 和 U 里的那些记录。字段顺序跟第一步保持一致，不然 UNION 出来的列会对错位。

第三步，两张中间表 UNION ALL，结果落进第三张物理表。合并在这步做完，不进覆盖语句。

第四步才是覆盖，完整语句只有一行核心：

```sql
INSERT OVERWRITE TABLE db.T
SELECT * FROM db.T_TMP_FINAL;
```

这条语句里既没有目标表的名字，也没有 UNION ALL。它只是把一张现成的表搬进另一张表的位置，没有需要合并的子目录，提交阶段也就没有那个窗口。

四步的完整脚本里，30 个字段要重复写两遍，篇幅比较长，这里就不全文贴了。

## 顺手挖出来的一个旧雷

原 SQL 里那个 NOT IN 子查询，用 `concat(uuid,DJXH)` 拼出来的键做比对。

NOT IN 有个老问题：子查询返回的结果里只要有一个 NULL，整个条件的结果就是 UNKNOWN，外面一行都匹配不上。换句话说，增量表里只要有一条被标成 U 或 D 的记录、uuid 或 DJXH 是空的，第一个分支就可能返回空集——覆盖之后目标表里只剩增量那部分。

这个雷在原来的写法里就埋着，跟这次的提交中断不是一回事。我在脚本里留了一行加固条件，默认没打开，因为它会改变边界行为。要不要加，得先确认历史数据里这些字段到底允不允许为空。

## 上线前盯住这几件事

数据恢复得先做。用备份把目标表回灌，行数对上了再动 SQL。表目录别直接删，先挪到隔离路径留着。

调度要停。恢复和改写期间，同一个任务的旧实例必须停掉，不能让第二条实例在旁边同时跑。脚本里关掉了并行，也给每次运行指定了独立的 staging 目录，避免两个实例撞在一起。

校验别省。四段 count 拉出来看一眼，两张中间表的和要等于结果表，结果表的行数要等于覆盖后目标表的行数。确认没问题再删中间表，中间表多留一个周期。

还有一件值得做的：把库里所有 INSERT OVERWRITE 扫一遍，只要 SELECT 里出现了目标表名，都记下来。这类写法平时不出事，出事就是整表级。
