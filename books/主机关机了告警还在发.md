# 主机都关机了，硬件告警还在发：带外 IPMI 监控怎么接

## 一、监控接法由取数位置决定

> 一句话结论：IPMI 监控的形态由取数位置决定，采集器排在第二步。

核完官方配置和指标文档才看清，先看数据从哪儿取，再选采集器，顺序反了会白装一遍。

| 维度 | 带内（主机 OS 内） | 带外（管理网直连 BMC） |
|---|---|---|
| 取数通道 | `/dev/ipmi0`，靠 ipmitool 或 FreeIPMI | RMCP / RMCP+ 走 UDP 623，或 HTTPS 走 Redfish |
| 主机挂了还有没有数 | 没有 | 有，关机、系统卡死、OS 未装都能采 |
| 部署形态 | 每台机器一个 agent | 一台采集机问一片 BMC |
| 权限 | root 或 udev 给设备节点授权 | BMC 只读账号加管理网可达 |
| 容器 | 需映射设备节点 | 官方注明容器仅适合远程采集 |
| 典型工具 | node_exporter textfile、Telegraf 本机模式 | ipmi_exporter 的 `/ipmi`、Telegraf 的 `servers`、Redfish 插件 |

单个 exporter 能探上千台设备。官方文档给的理由是，IPMI 设备在受管主机断电时仍然有数据，用不着一台机器配一个。

主机都关了，风扇、电源、温度这些读数还在，走的就是管理网这条通道。

## 二、七种接法

| 方法 | 取数 | 依赖 | 适合场景 | 主要限制 |
|---|---|---|---|---|
| ipmi_exporter `/metrics` | 带内，每台部署 | FreeIPMI 加 root | 单机、少量机器 | 容器用不了，主机挂了即失联 |
| ipmi_exporter `/ipmi` 多目标 | 带外 RMCP | FreeIPMI 加 BMC 账号 | 集中式，成百上千台 | 管理网要通，凭据集中管理 |
| Telegraf `inputs.ipmi_sensor` 转 `outputs.prometheus_client` | 两者都支持 | ipmitool | 已有 Telegraf 体系 | 只采 SDR、机箱电源、DCMI 功耗，没有 SEL |
| Telegraf 写 InfluxDB 或 VictoriaMetrics | 两者都支持 | ipmitool | 已有时序库，不想暴露端口 | 多一跳，指标名与 Prometheus 原生不同 |
| node_exporter textfile 或 Pushgateway | 带内为主 | 自写脚本 | 过渡期、临时巡检、自定义指标 | 超时、并发、陈旧数据都要自己兜 |
| Redfish 插件与厂商遥测推送 | 带外 HTTPS | BMC 固件支持 Redfish | 新机型、混厂商、要固件元数据 | 老 BMC 固件不支持 |
| 自写 exporter | 带外 | 自有代码 | 私有端点、定制指标 | 指标口径与会话池自己维护 |

先数一下机器规模。10 台以内带内脚本就够；到 300 台，逐台装 agent 和改凭据会先变成问题，集中式带外是更现实的选择。

## 三、方案一：一台采集机管一片

`ipmi_exporter` 有两个端点。`/metrics` 读本机，`/ipmi` 按 URL 参数探远端，后者是官方推荐的多目标模式。配置放在 `modules` 里，按机组复用。

```yaml
# ipmi_remote.yml，凭据用文件权限或密钥管理，别写明文
modules:
  default:
    user: "<bmc-user>"
    pass: "<bmc-pass>"
    driver: "LAN_2_0"
    privilege: "user"
    timeout: 10000
    collector_timeout: 20s
    collectors: [bmc, ipmi, chassis, dcmi, sel, sel-events]
    sel_events:
      - name: correctable_memory_error
        regex: "Correctable memory error.*"
  dcmi_only:
    user: "<bmc-user>"
    pass: "<bmc-pass>"
    privilege: "user"
    driver: "LAN_2_0"
    collectors: [dcmi]
```

`timeout` 的单位是毫秒，管 FreeIPMI 会话；它管不住子进程本身。`collector_timeout` 才是单个采集进程的墙钟上限，默认关闭，卡死的 BMC 会让子进程一直挂着并不断叠加。这一项必须开。

Prometheus 侧把 BMC 地址塞进 `target` 参数，再把 `__address__` 改成采集机地址：

```yaml
- job_name: ipmi
  params:
    module: [default]
  scrape_interval: 1m
  scrape_timeout: 30s
  metrics_path: /ipmi
  file_sd_configs:
    - files: ["/srv/ipmi_exporter/targets.yml"]
      refresh_interval: 5m
  relabel_configs:
    - source_labels: [__address__]
      target_label: __param_target
    - source_labels: [__param_target]
      target_label: instance
    - target_label: __address__
      replacement: "<采集机>:9290"
```

启动命令是 `./ipmi_exporter --config.file=/etc/ipmi_exporter/ipmi_remote.yml`。FreeIPMI 六件套要齐：`ipmimonitoring` 或 `ipmi-sensors`、`ipmi-dcmi`、`ipmi-raw`、`bmc-info`、`ipmi-sel`、`ipmi-chassis`，路径可以用 `freeipmi.path` 指定。

仓库 2026 年 11 月还有提交，最近一个 tag 是 2025 年 7 月的 1.10.1。生产上要么固定镜像摘要，要么自己构建，别指望 tag 跟上提交。

## 四、方案二：已有 Telegraf 体系怎么接

`inputs.ipmi_sensor` 底层调 ipmitool。填了 `servers` 走远程，留空就读本机 `ipmitool sdr`。

```toml
[[inputs.ipmi_sensor]]
  servers = ["<bmc-user>:<bmc-pass>@lanplus(<mgmt-ip>)"]
  interval = "60s"
  timeout = "20s"
  metric_version = 2
  sensors = ["sdr", "chassis_power_status", "dcmi_power_reading"]
  use_cache = true

[[outputs.prometheus_client]]
  listen = ":9273"
  path = "/metrics"
  expiration_interval = "120s"
```

`protocol` 要写 `lanplus`。官方示例里的 `lan` 对应 IPMI 1.5，凭据是明文过网的。`metric_version = 2` 会多出 `entity_id`、`status_code`、`status_desc` 三个标签，多内存槽和多风扇同名时靠它区分，Grafana 里才不会串线。

Prometheus 拉到的是快照，每次 scrape 不会触发新采集。Telegraf 按自己的 `interval` 采完把结果缓在内存，两边 interval 要分开设计。`expiration_interval` 也别留默认的 0，采集停了指标还停在最后一个值上，看起来一切正常，这种最难查。

本机模式需要设备节点权限，用 udev 规则 `KERNEL=="ipmi*", MODE="660", GROUP="telegraf"`，或者给 sudoers 配 ipmitool 免密。先用 `telegraf --test --input-filter ipmi_sensor` 验证输出，再重启服务。

## 五、方案三：Redfish 与推送式遥测

新机型的 BMC 用 HTTPS 加 JSON，比 RMCP 好管，也能顺带拿到固件版本这类元数据。Telegraf 的 `inputs.redfish` 从 1.17 起可用：

```toml
[[inputs.redfish]]
  address = "https://<mgmt-ip>"
  username = "<bmc-user>"
  password = "<bmc-pass>"
  computer_system_id = "System.Embedded.1"
  insecure_skip_verify = false
```

AWS 有一份规范性指导，专门讲这套接 Prometheus 与 Grafana。Dell iDRAC 10 还能反过来推：打开 `TelemetryService`，Telegraf 用 `inputs.http_listener_v2` 收 MetricReport，`json_v2` 解析后交给 `outputs.prometheus_client` 暴露，省掉逐台轮询和凭据下发。

| 路线 | 采集方向 | 凭据放在哪 | 规模上来以后 |
|---|---|---|---|
| ipmi_exporter 多目标 | Prometheus 拉采集机，采集机轮询 BMC | 采集机配置文件 | 轮询压力集中在采集机 |
| Redfish 插件 | Telegraf 逐台拉 | Telegraf 配置 | 每台都要配一次 |
| TelemetryService 推送 | BMC 主动推给 Telegraf | BMC 侧一次性配置 | 新增机器不用改 Telegraf |

混有机型时两套 exporter 并存就行，Prometheus 分 job 抓，指标名各自独立。2018 年以前的老 BMC 还得留 IPMI 那条路，具体固件版本门槛【需补充】。

## 六、轻量接法，以及自写出口

`node_exporter` 的 textfile collector 适合过渡。脚本定时把 `ipmitool sdr elist` 转成 `.prom` 文件丢进 textfile 目录，node_exporter 顺手带出去，不用多开一个端口。Pushgateway 更适合一次性巡检结果，持续指标放进去容易留下清不掉的旧序列。

碰到私有端点，改通用 exporter 往往要等上游适配。手上的 `bmc-redfish` 已经能巡一遍 Redfish，接监控有两条现成路：

| 接法 | 做法 | 代价 |
|---|---|---|
| textfile 输出 | CLI 按 Prometheus 文本格式写 `.prom`，交给 node_exporter | 改输出格式，加个定时任务 |
| 内置 `/metrics` | CLI 常驻并开 HTTP 端点，Prometheus 直接拉 | 自己管会话池、超时与并发 |

华为 iBMC 的私有端点、定制指标、会话复用这些细节，走自写出口比改通用 exporter 顺手，具体端点清单【需补充】。

## 七、指标覆盖与最短告警规则

| 关注点 | ipmi_exporter | Telegraf ipmi_sensor |
|---|---|---|
| 温度、风扇、电压、电流 | `ipmi_temperature_celsius`、`ipmi_fan_speed_rpm` 等分类指标 | `ipmi_sensor` 一个 measurement，靠 `unit` 与 `name` 区分 |
| 传感器健康度 | `ipmi_sensor_state`，0 正常、1 警告、2 严重、NaN 不适用 | `status`，1 正常、0 其他 |
| 整机功耗 | `ipmi_dcmi_power_consumption_watts` | `sensors` 加 `dcmi_power_reading` |
| SEL 事件 | `sel` 与 `sel-events` 两个 collector | 不支持，另跑 `ipmitool sel elist` |
| BMC 存活 | `ipmi_up{collector="..."}` | 无对应指标 |

`sel` 默认不启用，官方只开 `bmc`、`ipmi`、`chassis`、`dcmi` 四个。想盯内存可纠正错误和 SEL 条数，得自己写进 `collectors`，再用 `sel_events` 配正则分类计数。

```promql
ipmi_up{collector="ipmi"} == 0
ipmi_sensor_state >= 1
increase(ipmi_sel_logs_count[10m]) > 0
```

`ipmi_up` 得单独配一条告警。BMC 不响应时采集侧拿不到新样本，只看传感器状态的告警不会响。

## 八、几个容易踩的坑

| 坑 | 具体量级与做法 |
|---|---|
| SDR 缓存重建 | 官方配置文档写明：首次对某主机跑 `ipmi` collector 会重建 SDR 缓存，部分 BMC 耗时远超常规，`collector_timeout` 不要低于约 20s |
| `timeout` 不是硬超时 | 10000 毫秒只管 FreeIPMI 会话，卡死的 BMC 能无限挂住子进程，必须另配 `collector_timeout` |
| 采集间隔 | 60s 是社区经验下限，10s 级轮询会把共享网卡上的 BMC 打不响应，同一台别被两套系统重复采 |
| 串行采集的累乘 | collector 挨个跑，最坏耗时是 `collector_timeout × collector 数`，开 6 个就要按 120s 量级核 `scrape_timeout` |
| 凭据与权限 | 配置文件别写明文，Telegraf 支持 secret store；带内需要设备节点授权，`sel` collector 要更高 privilege |

SDR 缓存在两个方向上出过问题。此前那篇《内存槽都空了，监控还在报内存故障》里，缓存没重建，内存槽状态一直报着旧故障；这次核文档又看到另一头，首次对某主机跑 `ipmi` collector 要重建缓存，某些 BMC 上耗时把 scrape 直接拖超时。查这两类问题时，先看缓存的时间戳。

⚠️ 60s 与 10s 两个数字来自公开的部署记录，官方文档只给超时语义，没给轮询频率下限，自己 BMC 上的实测响应时长【需补充】。上生产前按 2 台机器压一轮。

## 九、上线顺序与待验证项

- 先画管理网拓扑，确认采集机能到所有 BMC 的 UDP 623 或 HTTPS 端口
- 给每台 BMC 建独立只读账号，凭据进密钥管理，别落进配置文件
- 单机手工验一遍 `ipmi-sensors` 或 `ipmitool sdr elist`，把传感器名字和单位记下来
- 选一条主链路先跑 7 天，把 `ipmi_up` 与采集耗时一起看
- 再补 SEL 与功耗，配 `sel_events` 正则，分开做告警规则
- 混机型时给 Redfish 与 IPMI 分 job，指标名不要混用
- 最后才做 Grafana 面板，按机柜分组，把 BMC 失联放在首屏

| 口径 | 内容 |
|---|---|
| 官方文档实证 | 两个端点、8 个可用 collector、默认 4 个、`timeout` 与 `collector_timeout` 语义、SDR 缓存重建、指标名、Telegraf 插件选项 |
| 社区经验值 | 60s 轮询下限、10s 级轮询打挂 BMC、混机型两套 exporter 并存 |
| 【需补充】 | 本号未连机实测，真实机群规模与单次采集耗时、华为 iBMC 私有端点在 Redfish 下的字段、老 BMC 固件版本门槛、私有化环境的管理网 ACL 策略 |

这次只核了文档，没有连机跑过一轮采集。真要上生产，先在 2 台机器上把 `collector_timeout` 和 `expiration_interval` 压一遍。

先在一台测试机上跑一次 `telegraf --test --input-filter ipmi_sensor`，看看能不能把传感器读全，再把命中的条数发留言区。不同 BMC 的传感器命名差得远，这个数我挺想知道。
