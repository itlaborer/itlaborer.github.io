# 扩容任务停在半路：没有取消按钮时怎么回滚

## 一、这份材料从哪来

> 一句话结论：添加节点任务暂停后，运营端只给继续、不给取消，收尾得走带回滚参数的管控接口。

翻到这份售后问答里的一页，才看清任务暂停后要靠接口回滚。

素材是一份本地的 TBase 售后问答文档，共 152 个条目。这次从中随机抽到「添加节点导致空间不足需要取消任务」，属于「添加／删除备机失败」分类。152 条里抽到这条算运气不错，现象、根因、处置、结论都齐了。

我这边只做了文档研读与脱敏整理，没有连现场环境，也没有复现这条处置路径。下面的现象、根因、接口字段与返回结果都按文档记录引用，凡文档没写的地方单独标出来。

## 二、停住之后页面是什么样

文档里的场景是私有化部署的 ARM 架构集群，管控版本 2.16.2.5。添加节点任务在 `BaseBackup` 步骤因为新节点主机空间不足被手动停止，任务随之暂停。

| 观察点 | 暂停后的状态 |
|---|---|
| 运营端节点列表 | 新增节点不显示 |
| 任务管理页面 | 没有「取消任务」按钮 |
| 新节点主机 | 节点进程仍然残留 |
| 任务本身 | 停在暂停态，只剩「继续任务」 |

节点列表里没有，主机上却还留着进程，这两处对不上。主机上跑着的那个进程最麻烦，页面看不见，清理的时候容易漏掉。

文档给的关键数字只有任务类型 `TbaseAddNode`、卡住的步骤 `BaseBackup` 和管控版本 2.16.2.5。主机剩了多少空间、任务跑了多久、残留几个进程都没记，这几处【需补充】。

## 三、根因在运营端的按钮里

文档把根因写得很短：2.16.2.5 版本的添加节点任务暂停后，运营端仅提供「继续任务」选项，不提供「取消任务」按钮。

卡住的地方在页面交互。磁盘不够只是把任务逼停的外部条件，真正让任务收不了尾的是暂停态缺一个取消入口。

| 层次 | 内容 | 处理方式 |
|---|---|---|
| 触发层 | 新节点主机空间不足，任务被手动停止 | 扩容前先算容量，这条属于前置检查 |
| 阻塞层 | 暂停态只有继续、没有取消 | 需要绕过页面，走管控接口并带回滚参数 |

只看触发层，会得出「把磁盘腾出来继续跑」这一个选项。新节点本来就是因为空间不够才停的，继续任务大概率再撞一次。

## 四、手工删进程之前

文档没写手工删除残留的步骤。按任务编排的一般逻辑，直接杀进程或者改元数据，任务状态还停在暂停，端口、磁盘占用和集群操作状态也没人恢复。这一段是我的推断，文档未验证，【需补充】。

⚠️ 任务编排系统一般把「取消」做成一段带补偿的动作，跳过它就得自己重写一遍回滚。「咨询产研后」这几个字在排查记录里很容易一眼滑过去，其实是这条路径的前置条件。

现场没有产研确认、也没有测试环境验证时，我不建议照着猜参数直接调生产接口。

## 五、接口怎么调

文档确认的做法是调用 `flowdriver` 的 `cancel` 接口，并把 `WithUndo` 设为 `true`。返回 `return_code` 为 1、`return_msg` 为 `OK`，表示请求被接受。请求长这样，字段值都换成了占位符：

```bash
curl -H "Content-Type: application/json" \
  -d '{"FlowId":"<任务号>","WithUndo":true,"session_id":"<session-id>","SessionId":"<session-id>","cluster_union_name":"<集群名>","region_id":"<region-id>"}' \
  <管控API>/api/v1/flowdriver/cancel/
```

返回示例：

```json
{"return_code":1,"return_msg":"OK","return_data":{}}
```

请求体里 `session_id` 与 `SessionId` 两个大小写形式都带，值是同一个会话标识，我照抄了文档，没敢合并。集群标识和地域标识也在请求体里，缺哪个字段会报什么错，文档里查不到。

`WithUndo=false` 会怎样、接口要不要额外鉴权、调用失败能不能重试，这三处都得现场核，【需补充】。

## 六、WithUndo 打开之后

文档说接口调用成功后，`flowdriver` 引擎自动执行回滚，完成四类动作。

| 回滚动作 | 对应前面的症状 |
|---|---|
| 停止节点进程 | 新节点主机上的残留进程 |
| 释放主机、端口、磁盘资源 | 空间不足与端口占用 |
| 清理节点元数据 | 节点列表里的异常状态 |
| 恢复集群操作状态 | 任务一直停在暂停态 |

对应关系是我按动作反推的，引擎内部按什么顺序跑、失败时停在哪一步、有没有中间态可查，文档都没写，【需补充】。

`WithUndo=true` 是这里唯一带语义的开关。它把取消任务变成取消加回滚，四个症状才一起被收掉。少了这个参数，页面上看不见的节点和主机上的进程还得另想办法。

## 七、回滚完看哪几处

验证命令和查询 SQL 文档里都没有。按上一节四类动作反推，至少得核对这几处，具体怎么查【需补充】：

| 核对点 | 期望状态 |
|---|---|
| 运营端任务列表 | 该任务不再显示为暂停中 |
| 节点列表 | 新增节点不再出现在待处理状态 |
| 新节点主机 | 进程、端口、临时目录回到添加前 |
| 集群操作状态 | 可以重新发起新的运维操作 |

这四条是我推的核对清单，文档里没有实测结果。做过的现场一般会在工单里留前后截图，那份材料我手上没有。

## 八、哪些字段必须换掉

这条问答里有一些不能带进公开文章的字段。整理时按固定规则统一占位：

| 原始字段 | 文中写法 |
|---|---|
| 工单号、任务号 | `<工单号>`、`<任务号>` |
| 集群标识 | `<集群名>` |
| 32 位会话标识 | `<session-id>` |
| 地域标识 | `<region-id>` |
| 管控接口域名 | `<管控API>` |
| 请求体里的项目与客户相关字段 | 同上占位 |

接口域名那一段我整段换掉了，它带的部署环境信息比集群名还多。请求路径 `/api/v1/flowdriver/cancel/` 保留，这条处置路径本身就靠它说清楚。

产品版本、任务类型、步骤名、`WithUndo` 这些都留着。管控版本 2.16.2.5 是根因的适用边界，删掉它读者会以为所有版本都缺这个按钮。

## 九、真碰上了按这个顺序走

- 先把任务号、任务状态、节点列表、主机资源占用截屏留证，别先动库或动进程
- 确认管控版本与任务类型，核对是否落在文档记录的范围内
- 走工单或产研渠道确认接口可用、参数口径与授权范围
- 在测试环境验证请求形态，再对目标任务发起带 `WithUndo=true` 的取消
- 记录返回结果，按第七节四项逐条核对回滚效果
- 回滚没做干净时保持任务原状，把前后证据交回产研，别叠加第二次操作

文档写死的部分和我的推断混在一起最容易出事，分开列一下：

| 口径 | 内容 |
|---|---|
| 文档明确记录 | 四个症状、根因、接口路径、`WithUndo=true`、返回码、四类回滚动作 |
| 运维推断 | 手工清理的风险、四类动作与症状的对应、四项核对点 |
| 【需补充】 | 其他版本是否同样缺按钮、`WithUndo=false` 行为、鉴权与重试、真实执行顺序、主机剩余空间数值、前后截图 |

本篇没有连现场、没有复现。文档记录能证明的是这条路径在该版本该场景下被用过，换版本、换集群形态还能不能照搬，得现场核。

## 十、和前几篇接得上

之前写过 TBase 备份失败的三层放大，那篇里任务卡住之后是 Center 重试队列和并发槽排满了。这篇卡住之后，页面连取消入口都没有，收尾要绕到管控接口。两处都得先看任务状态，再往下查资源。

回滚本身会改任务状态，动手前先把证据留下，这条取证纪律和前几篇一样。

翻一下自己手上的扩容流程，看任务暂停态有没有「取消」按钮。没有的话，把对应版本的处置路径提前问清楚，比现场临时翻文档省事。不同管控版本的任务状态机差别挺大，你们那边是怎么收尾的，留言区聊聊。
