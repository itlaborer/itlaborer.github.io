# 一套中间模型，撑起四种数据库迁移

## 一、先说结论

读完整套源码才看清，它并不是只能单向搬库。

这个名字带 `pg2mysql` 的工具，实际把四种方向都做了：PG 到 PG、MySQL 到 MySQL、PG 到 MySQL、MySQL 到 PG，方向由连接串前缀自动判定。撑起这四种组合的不是四份搬运代码，而是一套中间模型。

> 仓库 `github.com/itlaborer/pg2my`，产物 `pg2mysql` v0.2.0，Rust edition 2024，Apache-2.0。本文为静态源码阅读，未编译、未连库运行；凡属推断或未能实测的地方，均单独标注。

先看它要覆盖的场景：

| 场景 | 对应能力 |
|---|---|
| 整库搬家，含表结构、主键、索引、外键、注释、枚举、数组、生成列 | 结构迁移 + 全量搬运 |
| 只同步几张表、排除几张表、只搬满足条件的行 | 表过滤与条件过滤 |
| 大表搬到一半断了 | 断点续搬，表级跳过 + 行级位置 |
| 全量之后还要跟上源库变更 | 水位轮询或日志增量 |
| 目标表已存在且结构落后 | 自动补列、补索引 |
| 上线前想先看会执行什么 | 只打印建表语句或搬运计划 |

定位很清楚：运维在自己机器上跑的单二进制工具，没有消息队列、没有服务端、没有常驻进程（增量阶段除外）。对标的是手工拼导出导入脚本、DataX、Debezium 一类方案，取舍是拿「轻」换「不做到企业级增量」。

## 二、中间模型才是主干

整个项目最关键的一层，是把两端数据库都翻译成同一套描述。

```text
PG 源      pg_catalog / pg_attribute   ┐
MySQL 源   information_schema          ┘ → 内省
                    ▼
        Table / Column / ColumnKind
        Index / ForeignKey
        Value { Null, Text, Bytes }     ← 中间表示
        type_map / value                ← 语义类型与值转换
                    ▼
PG 目标    DDL + COPY / INSERT         ┐
MySQL 目标 DDL + 批量 INSERT          ┘ → 生成
```

`Source` 和 `Sink` 是两个枚举，按方言分派到四个实现文件。四种迁移方向于是退化成「两个前端 × 两个后端」的组合，将来加一种数据库，只要补一对前端和后端，中间那层不用动。

第二个关键决策是**值统一走文本**。读源库时把每列写成形如文本输出的表达式，布尔、时间、二进制各用专门表达式处理；写目标库时再让目标库自己转回目标类型。好处是完全绕开两套驱动各自的类型系统，不必为每种列类型写转换实现。代价是所有方言差异都得手工兜底：无符号大整数、数组转 JSON、枚举序号、集合位图、零日期，这些散落在类型映射和日志解析代码里的特殊处理，本质都是这个决策欠下的账。

## 三、四个值得单拎出来的设计

### 3.1 并行时还能看到同一时间点

源库不同，做法不一样，这一点值得单独说：

| 源 | 一致性做法 |
|---|---|
| PG | 主连接导出快照标识，每个并行任务各自挂到该快照；导出连接必须保活到搬运结束 |
| MySQL | 每个任务自己开启一致性快照事务 |

⚠️ 这里有一处**源码与项目说明文档的口径差异**：说明文档写「并行任务共享同一快照」，但 MySQL 分支是各任务各开一个一致性事务，属于各自的一致性读，不是 PG 那种共享快照标识。跨表严格一致性在 MySQL 侧不能按 PG 的口径理解。这一条是源码实证，不是猜测。

### 3.2 并行是按表，不是按行

信号量加任务集，一张表一个任务，各连各的源和目标；单表内部是串行主键分页。所以加大并行度对**一张超大表没有加速效果**，只在表多的时候有效。

建表顺序也被拆成阶段，顺序不能乱：先建命名空间与表，再比对目标补列补索引，接着**摘掉目标已有外键**（否则清空目标表会被引用关系挡住），然后并行搬数据，数据落完才建索引、加注释、重建外键、把序列推到最大值。`--verify` 的行数比对放最后。补列一律按可空加，避免存量行让「加非空列」直接失败。

### 3.3 断点分两级

断点是一个 JSON，落盘用「先写临时文件再改名」的原子方式。

- **表级**：已完成的表整表跳过。
- **行级**：仅在开启续搬且为**单列主键**时启用，条件里带上一次位置和排序，每批成功后回报该批最大主键，最多每秒落盘一次，续搬时用覆盖写吸收边界上可能重复的行。

一个容易踩的坑：清空目标表的开关会同时清掉已完成表、行级位置和增量位点。因为目标被清空了，旧断点不再可信，等于全量重来。

### 3.4 增量是两条完全不同的路

| 对比项 | 水位轮询 | 日志增量 |
|---|---|---|
| 适用源 | PG / MySQL 均可 | 仅 MySQL，PG 源会被明确拒绝 |
| 水位/位点 | 自动探测更新时间列，找不到退回主键第一列 | 全量开始前记下日志文件名与位置 |
| 能捕获 | 新增、更新，**抓不到删除** | 新增、更新、删除 |
| 前提 | 表要有主键，否则跳过 | 需开启行格式日志、完整行镜像与复制权限 |
| 位点推进 | 每轮取本批最大水位写回 | 只在事务提交事件推进，中断也先存位点 |

PG 源**没有实现逻辑复制**，项目说明里列为已知限制。日志路径里还有不少硬活：集合位图、枚举序号、无符号大整数、MariaDB 时间戳都要专门还原；主键被更新时先删旧行再写新行；部分行更新事件直接跳过并告警。

## 四、怎么用：先预演，再落地

编译需要较新的 Rust 工具链，老系统可以编静态 musl 版本，锁文件建议带上以保证可复现：

```bash
cargo build --release --locked
cargo test
```

参数不少，日常真正要记的是这几个：

| 参数 | 作用 |
|---|---|
| `--source` / `--target` | 连接串，前缀决定迁移方向，必填 |
| `--tables` / `--exclude-tables` | 表白名单 / 黑名单，后者优先级更高 |
| `--batch-size` / `--parallel` | 每批行数 / 并行表数，为 0 会直接报错 |
| `--truncate` | 写前清空目标表，同时清掉断点 |
| `--copy` | PG 目标走批量装载，覆盖写时自动退回普通插入 |
| `--ddl-only` / `--dry-run` | 只看建表语句 / 看建表语句加搬运计划 |
| `--checkpoint` / `--resume` | 断点路径 / 续搬，续搬必须配断点路径 |
| `--cdc` / `--cdc-mode` | 开启增量 / 选择轮询或日志模式 |
| `--verify` | 迁完比对每张表行数 |
| `--where` | 附加到每张表源查询的原始条件 |

注意两个反直觉点：只打印建表语句或预演时**仍会连源库做内省**，只是不连目标库、不写数据；带条件过滤时别开行数校验，因为校验比的是整表行数。

密码建议走环境变量，不进命令历史，也不进进程列表：

```bash
read -rs PGPASSWORD; export PGPASSWORD
read -rs MYSQL_PWD;   export MYSQL_PWD

pg2mysql --source postgres://app@<源IP>:5432/appdb \
         --target mysql://app@<目标IP>:3306/appdb
```

跨方言时两个变量可以同时设置；连接串里已经带了密码，环境变量就不生效。

上线前的两条预演命令，建议一次都别省：

```bash
pg2mysql --source postgres://app@<源IP>:5432/appdb \
         --target mysql://app@<目标IP>:3306/appdb --ddl-only

pg2mysql --source postgres://app@<源IP>:5432/appdb \
         --target mysql://app@<目标IP>:3306/appdb --dry-run
```

重点核对类型映射结果：无符号大整数、数组、时间时区列、长文本索引前缀。这几类最容易在目标库上变形。

大表带断点的正式搬运：

```bash
pg2mysql --source postgres://app@<源IP>:5432/appdb \
         --target mysql://app@<目标IP>:3306/appdb \
         --tables big_events --batch-size 5000 --parallel 4 \
         --checkpoint /var/tmp/pg2mysql.json --resume
```

中断后原样重跑同一条命令即可。MySQL 源做日志增量时，务必在同一次命令里带上断点路径，程序会在**搬数据之前**记位点，这样全量期间发生的变更也能补上。

落地顺序按这个走：

- 目标库先备份，确认命名空间可建、字符集正确。
- 预演看建表语句，再看搬运计划，确认表名按实际存储名填写。
- 挑一两张小表带清空目标表和行数校验试迁，比对行数并抽样看内容。
- 全量阶段给大表配断点、续搬和合适的批量大小。
- 全量完成后再开增量；行数校验只比行数，跨库业务对账仍需自己写核对语句。
- 权限按最小集给：源库只读，目标库建表写入，日志增量另加复制相关权限。

## 五、源码读出来的边界，和文档没写的风险

把「已确认」和「待验证」分开，是这次读源码最该留下的习惯：

| 项 | 定性 |
|---|---|
| MySQL 并行并非共享快照 | ✅ 源码实证，与说明文档措辞有出入 |
| 条件过滤参数是原始语句直接内联 | ✅ 源码实证，仅限可信输入，别拼不可信内容 |
| 并行度对单表无效 | ✅ 源码实证，信号量按表分配任务 |
| 批量装载仅用于 PG 目标且非覆盖写 | ✅ 源码实证，条件写死在分派处 |
| 轮询抓不到删除、无主键表跳过 | ✅ 源码与文档双重确认 |
| PG 源没有逻辑复制 | ✅ 文档明确列为限制 |
| 日志实例的编号取进程号，多实例可能撞号 | ✅ 源码实证，建议错开运行或改造 |
| 导出快照的长事务是否拖住源库清理 | ⚠️ 由机制推断，需现场评估【需补充】 |
| PG 侧未启用传输加密，遇强制加密服务端的行为 | 【需补充】未实测 |
| 实际吞吐、大表耗时、与定制内核的兼容性 | 【需补充】未编译未连库，无法评估 |

最后三行不是「工具不行」，而是本次只读了代码、没有跑起来的诚实边界。真要上生产，这三格必须换成现场实测数据。

## 六、和此前两篇的呼应

这套「全量 + 断点 + 水位或日志增量」的结构，和之前写过的两库表同步方案选型、一次性迁移手册是同一问题的两条路。那两篇是**用数据库原生能力拼**（逻辑复制、定制格式导出、外部表），本篇是**把搬运逻辑收进一个二进制**。

原生方案胜在不丢语义，工具方案胜在跨方言、两端不必装扩展、可以断点续搬。生产选型时按三点切就够了：两端是否同构、是否需要持续增量、能否接受建表变更不同步。
