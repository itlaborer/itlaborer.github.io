# 查询库备份三道坎：凭据、并发槽、配置优先级

## 一、三条记录放在一起看

> 一句话结论：凭据文件、agent 并发槽、auto.conf 覆盖，按备份推进顺序逐层查完，再复跑一次全量备份。

备份连着卡了三回，三处都在配置层。

现场留下来的是 3 条记录，每条一两句话，写了现象和当时怎么绕过去，报错原文一句没留。我这轮没连现场库，也没复现，做的是记录梳理和翻官方文档。

| 次序 | 现象 | 层次 | 现场做法 |
|---|---|---|---|
| 1 | 管控里加了 COS 设置，配置文件没生成 | 凭据落地 | 按格式手写，同步到所有节点 |
| 2 | 同一台服务器上备份节点超过 2 个 | agent 并发槽 | 把并发任务数上限调到 2 以上 |
| 3 | 备份最后校验 WAL 失败 | 参数生效值 | 移除 auto.conf 里的归档命令并重载 |

第一处卡在文件有没有写下来，第二处卡在单机上能同时跑几份拷贝。第三处更绕，同一个参数被两个文件各写了一遍，最后生效的是后读的那份。

## 二、一次备份要经过哪些地方

管控先在页面上收 COS 设置，落成本地文件；agent 领到任务后按并发额度起拷贝，数据经限速和分片传进对象存储；最后一步校验 WAL 归档。

3 条记录分别落在下发、拷贝和收尾，中间传数据那段没出问题。

顺序有讲究。凭据文件没落地的时候去调并发参数，任务压根到不了那一层，看不出改没改动。至于每一处具体的报错文本，任务日志长什么样【需补充】。

## 三、第一道：管控加了设置，文件没落地

管理员账号在管控里加完 COS 设置，约定位置该有的那个文件没生成。后来照同事给的格式手写一份，同步到所有节点，任务才走下去。

路径和文件名我做了泛化，下文统一记作 `<cos-config>`。记录里一处写相对路径，另一处写带前导点的绝对路径，是不是同一个文件【需补充】。差一个点，读配置的进程就找不着，这个先核。

公开工具的配置长这样，`[common]` 段里放密钥、桶和地域。现场那份模板是不是同一套字段【需补充】：

```ini
[common]
secret_id = <secret-id>
secret_key = <secret-key>
bucket = <bucket>
region = <region>
endpoint = <endpoint>
max_thread = 5
part_size = 10
```

工具默认从运行用户家目录读，也能用 `-c` 指到别处。文件放对位置只算一半，还得看读它的那个进程认哪条路径。

明文密钥就在这个文件里。同步完核对属主和权限，600，属主给 agent 的运行用户。截图、工单附件里出现过的密钥一律占位，登过截图的建议直接轮换。

第一道还欠 4 个答案：

- 管控为什么没把文件写出来，是目录权限、磁盘，还是 agent 没刷新
- 文件名与路径是否和读取方约定一致
- 同步范围覆盖哪些节点，CN、DN、管控节点各算不算
- 文件属主、权限，以及同步后有没有被覆盖回旧版本

## 四、第二道：一台机器上落了 2 个以上备份节点

记录里那句很直接：把 `MAX_AGENT_COPY_DATA_TASK_NUM` 调到大于 2。这个参数我在公开文档里翻不到，看名字是管控或 agent 内部的。

参数写在哪个文件、改完要不要重启 agent、上限多少、按主机还是按任务计数，4 项都【需补充】。连失败时是排队、超时还是直接报错，记录里也没提。

之前写过备份失败的三层放大，那篇里有个 `copyDataStepTaskNum=2`。两个名字都带 2，我一开始差点归到一处，翻回旧稿才分开：

| 参数 | 所在侧 | 管什么 |
|---|---|---|
| `copyDataStepTaskNum` | Center / OSS 调度侧 | 一次任务里能并行推进的拷贝步骤 |
| `MAX_AGENT_COPY_DATA_TASK_NUM` | 单机 agent 侧 | 这台机器上能同时跑的拷贝任务数 |

一个卡调度，一个卡单机。改错了地方，任务照旧排队。

并发额度一放开，瓶颈就往下挪。之前那篇记过 `pv --rate=50`、`COS_TOOL_PART_SIZE` 与 `WORKER_SIZE`，还有管控版本 2.15.21.2 起加的带宽限制，都会接着顶上来。

同时跑 3 份拷贝，网卡和本地盘也跟着吃紧，任务未必更快。这段是我按经验猜的，现场没给监控数据。

## 五、第三道：数据传完了，WAL 校验没过

第 3 条最费琢磨：数据都传完了，最后校验 WAL 备份时失败。记录给的处置是下面两句，执行完就恢复了。

```sql
ALTER SYSTEM RESET archive_command;
SELECT pg_reload_conf();
```

原因写的是 `archive_command` 取自 `postgresql.auto.conf`，把定制配置文件里的值压住了。我一开始以为是归档脚本没配好，翻完官方的配置读取顺序才改口：

| 口径 | 内容 |
|---|---|
| 读取顺序 | `postgresql.auto.conf` 与 `postgresql.conf` 都会读，前者的设置覆盖后者 |
| 写入方 | `ALTER SYSTEM` 写进 `postgresql.auto.conf` |
| RESET 的作用 | 只移除该参数那一条，`RESET ALL` 会清空整个文件里的条目 |
| 执行限制 | 需要超级用户或被授予该参数的权限，不能放在事务块或函数里 |
| 关闭入口 | 官方文档列了 `allow_alter_system=off`，可禁用 `ALTER SYSTEM` |

`archive_command` 是 sighup 级别，重载够用。`archive_mode` 是 postmaster 级别，动它得重启实例，两条别顺手一起改。

归档命令失效那阵子，已经生成的 WAL 段会留在 `pg_wal` 等归档，磁盘慢慢涨上去。校验失败和空间上涨，多半是同一件事的两头。

查生效值先看它从哪个文件来：

```sql
SELECT name, setting, source, sourcefile, sourceline, pending_restart
FROM pg_settings
WHERE name IN ('archive_command', 'archive_mode');

SELECT * FROM pg_file_settings WHERE name = 'archive_command';

SELECT * FROM pg_stat_archiver;
```

`pg_settings` 里的 `sourcefile`、`sourceline` 会直接指出文件和行号。非超级用户又没有 `pg_read_all_settings` 权限时，这两列是 NULL。

`pg_file_settings` 能看各文件里的条目有没有 applied，`pg_stat_archiver` 看归档成败和最后一次失败的时刻。

`postgresql.conf.user` 是 TBase / TCHouse 的定制文件，公开资料查不到，谁引入、在哪一行引入【需补充】。有一处可以先排除：`include_dir` 按官方规则只收目录下以 `.conf` 结尾、且不以点开头的文件，`postgresql.conf.user` 不在里面。现场多半走显式 `include`，或者管控拼接时写进去的，得看实例上实际怎么配。

## 六、分布式里最容易漏的一步

`ALTER SYSTEM RESET` 和 `pg_reload_conf()` 都只管当前连上的那个实例。分布式里每个 CN、每个 DN 各自一份 `postgresql.auto.conf`。

在一个节点上跑完，只修好一个节点。漏掉的那个，下次备份轮到它还会报同样的错。

还有个会让问题回来的地方：auto.conf 里那条归档命令当初是谁写的，记录里没说。管控要是周期性下发参数再写回去，手工 RESET 顶得了一阵。查写入方比反复 RESET 划算。

| 核对点 | 位置 | 期望结果 |
|---|---|---|
| 参数生效值 | `pg_settings.sourcefile` | 指向定制配置文件 |
| 各文件条目 | `pg_file_settings` | auto.conf 里已无该参数 |
| 归档是否恢复 | `pg_stat_archiver` | 失败计数停止增长 |
| 待重启标记 | `pg_settings.pending_restart` | 为 f |
| 节点覆盖 | 所有 CN 与 DN | 逐节点结果一致 |

`RESET ALL` 顺手不得，它会把 auto.conf 里所有条目一起清掉，里面可能还有别人加的运维参数。

## 七、哪些是确认的，哪些是推的

| 口径 | 内容 |
|---|---|
| 现场记录 | 3 条现象、3 条处置做法、参数名与 SQL 原文 |
| 官方核对 | 配置文件覆盖顺序、RESET 语义、权限限制、参数生效级别、include_dir 规则 |
| 运维推断 | 备份链路的四段划分、并发额度放开后的瓶颈位置、复发路径、逐节点核对清单 |
| 【需补充】 | 管控未生成文件的原因、路径与文件名是否一致、agent 参数出处与生效方式、定制文件引入方式、auto.conf 写入方、任务日志原文 |

这轮没连现场库，没复现。3 条处置在那个版本、那个集群形态上被用过，换版本能不能照搬，得现场核。

## 八、真碰上了按这个顺序走

- 留证：管控任务日志、agent 日志、节点上的配置文件清单与权限、报错原文
- 查第一道：确认凭据文件存在、字段齐全、权限 600、所有相关节点都有同一版本
- 查第二道：数清同一台机器上的备份节点数，核对并发参数，调完后观察下一轮任务
- 查第三道：用 `pg_settings.sourcefile` 确认归档命令来自哪个文件，再看 `pg_stat_archiver`
- 执行 `ALTER SYSTEM RESET archive_command` 与 `SELECT pg_reload_conf()`，所有 CN 和 DN 逐节点做
- 复跑一次全量备份，盯着最后的 WAL 校验，同时看 `pg_wal` 有没有继续堆积
- 隔一轮再看 auto.conf，确认没有别的进程把参数写回来

## 九、和前几篇接得上
