# 同一张表，直查和落表差了一百多倍

## 一、先把现象摆清楚

> 一句话结论：写入语句里只要还留着对视图的查询，大小函数就会在数据节点上重算一遍；先把值在协调节点固化成常量，再落表，数才对得上。

表大小直查对得上，一落表就少了一百多倍。九万多行一行没少，缩的是数值本身。

现场给的是两张查询截图。一张是在协调节点上直查一张统计视图，另一张是用建表语句把同一批数据写进结果表之后复查。库名、视图名、结果表名都做了占位。

| 查法 | 行数 | 大小合计 | 口径 |
|---|---|---|---|
| 协调节点直查视图 | 91679 | 469405 GB | 全库 |
| 建表语句落到结果表 | 91679 | 3736 GB | 单个分片 |
| 两者比值 | 相同 | 125.6 倍 | 行数一致 |

提交之后再测一次，还是 3736 GB。未提交和快照假象这两条可以划掉。

## 二、先排除三个想当然的判断

我一开始以为是结果表的分布键把行聚到了一个数据节点，也想过是不是只查到了部分表。行数摆在那里，91679 行全落进去了，这两条都不成立。

真正变的是每一行里那个大小值。视图定义用的是 `pg_total_relation_size(pg_class.oid::regclass)`，跟最初描述的 `pg_table_size` 不是一个函数。截图里能看到视图带模式名、表名、属主和大小几列，大小的单位是 GB，完整定义【需补充】。

官方口径写得很直接：连协调节点时 `\dt+` 看到的表大小是所有数据节点之和，连数据节点时只是该节点的大小。目录和统计视图每个实例各存一份，两边内容本来就不同。

两个执行计划逐行相同，都是本地的顺序扫描加哈希连接加排序，没有跨节点算子。这点容易读错：它展示的是视图展开后的协调节点本地计划，没暴露建表语句真实的下发路径，不能拿来当作没有下推的证据。

## 三、把节点数放回拓扑里算一遍

现场口述的拓扑是 44 台物理机，每台放 6 个节点，按一组 1 主 2 备来分。44 乘 6 得 264 个实例，再除以 3，正好 88 个主分片。副本数到底是 1 主 2 备还是 1 主 1 备【需补充】，下面按前者算。

| 口径 | 计算 | 结果 |
|---|---|---|
| 按 88 个主分片摊 | 469405 除以 88 | 5334 GB，约 5.21 TB 每主分片 |
| 按 44 台机器摊 | 469405 除以 44 | 10668 GB，约 10.42 TB 每台 |
| 若按 264 个实例摊 | 469405 除以 264 | 1778 GB，约 1.74 TB 每实例 |
| 落表拿到的值 | 3736 GB | 约 3.65 TB |

第一行跟扩容材料里每数据节点有效 5T 几乎吻合。第三行量级对不上，说明协调节点求和是按 88 个逻辑主分片算的，备副本没有计进去。

3736 GB 相当于平均值的七成，可以理解为 88 个主分片里偏空约 30% 的那一个。分布式库里节点负载不齐很常见，新扩容的节点、刚迁移完的分片都会这样。

这里要收回我上一轮的一个判断。当时看到 125.6 倍，觉得像是全库等于单节点乘以节点数的形状。88 这个数出来之后账就清楚了，125.6 只是全库除以一个偏空主分片，既不是节点数，也不是统一倍率。

还有一处材料冲突要记下。旧扩容记录写的是 44 台乘 5 个节点等于 220，这次是 44 台乘 6 个等于 264。两套口径不同，做容量测算时不能混用，得注明取自哪套集群、哪个时间点【需补充】。

## 四、缩水发生在写入路径上

分布式优化器处理建表语句和插入查询语句时，会把对视图的扫描连同大小函数一起下发。大小函数和目录表都是实例本地语义，落到哪个实例就报哪个实例的存储占用。写入语句里只要还留着查询，这个值就会被重新求值一次。

| 写法 | 大小函数在哪求值 | 结果 |
|---|---|---|
| 建表语句带查询 | 数据节点本地 | 缩水 |
| 插入语句带查询 | 数据节点本地 | 缩水 |
| 物化 CTE 再插入 | 大概率仍在数据节点 | 不保证 |
| 客户端导出再导入 | 协调节点，结果已固化 | 正确 |
| 插入语句用常量值 | 协调节点，常量不再求值 | 正确 |

后两条是语义上确定的路。客户端先把结果集接住，值已变成普通数字，再灌回去时不带任何函数。

带三副本的集群还有个坑。逐节点采集时若把备实例也加进汇总，全库会乘 3，得到约 1.4 PB 的物理占用。

动手前得先确认节点表返回的是 88 个逻辑分片名还是 264 个实例名，并把主备占用分开【需补充】。这个量按逻辑还是物理核算，也待确认。

## 五、两种能把值写准的姿势

第一种最省事，用客户端侧的 copy 元命令。结果集以字节流拉回本地，不走服务端下推。

```bash
psql -h <cn-host> -p <port> -U <user> -d <db> \
  -c "\copy (SELECT nspname, relname, t_owner, t_size FROM <view>) TO '<snap>.csv' CSV HEADER"

psql -h <cn-host> -p <port> -U <user> -d <db> \
  -c "\copy <result>(nspname, relname, t_owner, t_size) FROM '<snap>.csv' CSV HEADER"
```

现场若用图形客户端或 JDBC，改走服务端 COPY 的标准输入输出形式，道理一样。

91679 行不能塞进一条 SQL，按每批 1000 行拼常量。下面这段生成可执行的 SQL 文件，任何客户端都能跑。

```python
import csv, io

BATCH = 1000
TABLE = "<result>"
COLS  = "nspname, relname, t_owner, t_size"

def esc(v):
    if v is None or v == "":
        return "NULL"
    return "'" + str(v).replace("'", "''") + "'"

rows = []
with io.open("<snap>.csv", encoding="utf-8") as f:
    for r in csv.DictReader(f):
        rows.append("(%s,%s,%s,%s)" % (
            esc(r["nspname"]), esc(r["relname"]),
            esc(r["t_owner"]), r["t_size"]))

with io.open("insert_size.sql", "w", encoding="utf-8") as out:
    for i in range(0, len(rows), BATCH):
        out.write("INSERT INTO %s (%s) VALUES\n%s;\n\n"
                  % (TABLE, COLS, ",\n".join(rows[i:i+BATCH])))
    out.write("ANALYZE %s;\n" % TABLE)
```

数值列不加引号，保住 numeric 精度。数据节点按目标表分布键路由每一行时，不会对常量再算一次，全库的值就能完整落表。

建表时有几处要留意：

- 结果表显式指定分布键，按模式名加表名哈希，现场语法【需补充】
- 别建成复制表，否则每行在 88 个主分片各存一份，看到的表大小会被放大
- 大小列用 numeric，灌完跑一次 ANALYZE
- 复查时若合计仍是 3736 GB，检查是不是又绕回了插入查询语句

一定要单条 SQL 写完的话，可以试物化 CTE，但它只挡 SQL 重写层的内联，挡不住分布式规划器下发内部扫描。dblink 连回协调节点自己能强制上下文，却要装扩展、带鉴权，绕得比导出导入更远。这两条我都没拿它当生产口径。

## 六、落表之后怎么验

```sql
SELECT count(*), sum(t_size) FROM <view>;
SELECT count(*), sum(t_size) FROM <result>;

SELECT count(*) FROM (
  SELECT nspname, relname FROM <view>
  EXCEPT
  SELECT nspname, relname FROM <result>
) d;

SELECT count(*) FROM <view> v
JOIN <result> r USING (nspname, relname)
WHERE v.t_size IS DISTINCT FROM r.t_size;

SELECT round(min(x), 2), round(max(x), 2), round(avg(x), 2)
FROM (
  SELECT v.t_size / nullif(t.t_size, 0) AS x
  FROM <view> v JOIN <result> t USING (nspname, relname)
) s;
```

前两句的行数与合计要对齐，缺行检查和值不一致检查都该返回 0。最后一句看逐表比值是否散得开，散得开就印证节点偏空，若收在一个固定整数附近，得回头查副本计数。

还欠几项现场验证：

- 逐节点取全库合计，确认 3736 GB 落在哪个主分片
- 视图里的哈希连接有没有把行放大，对比总行数和去重后的表数
- 分区父子表和复制表是否被重复计数
- 执行计划里下发的节点组，以及数据节点日志中实际运行的 SQL

## 七、哪些是确认的，哪些还在猜

| 结论 | 依据 | 属性 |
|---|---|---|
| 行数没少，缩的是大小值 | 两次 91679 行，提交后合计不变 | 确认 |
| 协调节点求和，数据节点报本地 | 官方表操作文档 | 确认 |
| 88 个主分片，每片约 5.21 TB | 44 台乘 6 除以 3 自洽，与 5T 盘容量吻合 | 推测，待节点表核实 |
| 3736 GB 是偏空约三成的分片 | 与平均值之比为 0.7 | 推测，待逐节点实测 |
| 大小函数在写入路径被重新求值 | 函数本地语义加下发行为，与现象吻合 | 推测，待执行计划实证 |
| 约 1.4 PB 物理占用 | 按三副本推算 | 推测，待容量口径确认 |

前两行是文档和现场数据能落定的。中间几行都建立在 1 主 2 备这个口述前提上，副本数一旦是 1 主 1 备，第三节的整张表要重算。
