# 5.5T 的 pgsql_tmp，先别急着删文件

## 一、现场：一个 DN，5.5T

> 一句话结论：临时目录暴涨，先按文件名里的 pid 找到源头会话，杀进程比删文件管用。

汇聚区一个 DN 的临时目录涨到 5.5T，最大单文件 1.4T。先别删文件，从文件名里抠出进程号。

现场信息不多：DN053 主节点，pgsql_tmp 目录 5.5T。截图是目录里的一屏 `ls -l`，不是全量。后面还有没有更大的文件，【需补充】。

## 二、先看清楚是谁写的

把截图按大小排一遍，格局一下就清楚了。

| 文件名（脱敏后）                       | 字节数               | 约合      | 时间                  |
| ------------------------------ | ----------------- | ------- | ------------------- |
| `pgsql_tmp4465.2`              | 1,544,270,569,472 | 1.40 TB | 11-23 08:16         |
| `pgsql_tmp4465.0`              | 439,046,511,104   | 409 GB  | 11-23 06:54         |
| `pgsql_tmp4465.1`              | 139,556,289,897   | 130 GB  | 11-23 03:03         |
| `pgsql_tmp4465.0.<session-id>` | 141,118,957       | 135 MB  | 11-23 03:01         |
| `pgsql_tmp13428.*`             | 2 MB 级            | —       | 11-23 07:59 至 23:08 |
| `pgsql_tmp52096.0`             | 284,278,784       | 271 MB  | 11-23 08:15         |
| `pgsql_tmp4005.*`              | 21,110,320        | 20 MB   | 11-23 07:53         |

命名规则就三层：`pgsql_tmp<pid>.<fileno>[.<session_id>]`。

- 4465 是 DN 上的 backend 进程号
- 中间那个 0、1、2 是文件序号
- 末段长数字是会话标识，文中统一写成 `<session-id>`

4465 一个进程占了 1.4T + 409G + 130G，其余 pid 加起来不到 400 MB。目标明确，不用全目录扫一遍。

这里插一句：`.0`、`.1`、`.2` 别当成三个独立问题。同一个 pid 下的三个文件，多半是同一次查询落盘的几个分片。真按三个故障去查，会绕远。

## 三、为什么先杀进程，不先删文件

删文件的效果很直观：磁盘立刻回一块，看着痛快。但写入方还活着，tmp 会继续长。5.5T 这种量级，删完过一会儿又冒出来，而且现场没了——文件名里挂着的 pid 和会话标识一起被你删掉了。

杀进程是另一条路。源头停了，临时文件由数据库自己回收，不需要手工 `rm`。

也有必须让步的时候。剩余空间已经小到威胁实例，比如快把数据目录挤爆，那就止血优先：先把最大的那个文件挪走或删掉，再回头定位。这是两害相权，不是标准动作，得记在工单里。

⚠️ 还有个细节容易被忽略。文件正被后端进程持有句柄时，`rm` 掉并不会马上释放空间，要等句柄关闭。所以"我删了，怎么 df 没变化"这种疑问，答案通常在这儿。

## 四、四步把源头揪出来

这一步要绕个弯。DN 上看到的 4465 是 DN 本地的 backend 号，CN 上另有一套 pid，两边对不上。所以得先靠 DN 日志把会话和 CN 串起来，再回 CN 查。

**第一步，确认最大文件的 id。** 已经做完了，就是 4465。

```bash
cd <pgsql_tmp目录>
ls -lhS pgsql_tmp* | head -20
du -ab pgsql_tmp* | sort -rn | head -5
```

**第二步，在 DN 的 pglog 里查对应的 CN 和 pid。**

```bash
cd <DN日志目录>
grep -nE "4465|<session-id>" postgresql-2026-11-23*.log | tail -100
```

在输出里找带 coordinator、cn、host 字样的行，`host` 一般就是 CN 的地址，同一行会带出 CN 侧的 pid。不同版本的日志字段差别不小，具体字段名【需补充】，别照抄我这几个关键词硬套。

**第三步，登录对应 CN，查用户和语句。**

```sql
SELECT pid, usename, datname, client_addr, state,
       query_start, now() - query_start AS runtime,
       left(query, 500) AS query
FROM pg_stat_cluster_activity
WHERE pid = <cn-pid>;
```

视图名是 `pg_stat_cluster_activity`，`activity` 这个词容易少敲一个字母。如果这个 pid 已经不在了，用会话标识兜底再查一次。

**第四步，杀掉会话。**

```sql
SELECT pg_cancel_backend(<cn-pid>);
SELECT pg_terminate_backend(<cn-pid>);
```

先 cancel 再 terminate，给会话留一个自己收尾的机会。回 DN 复核 4465 是否还在，CN 侧终止后 DN 进程仍存活的话，再在本地补一刀：

```sql
SELECT pg_terminate_backend(4465);
```

## 五、还没确认的那一步

写到这里得停一下，把话分清楚。

能确认的只有一件事：pid 4465 写出了至少 1.4T 的临时文件，时间跨度从 03:01 到 08:16。

至于它为什么写出这么多，我只能给几个方向，都算推测：排序或 hash 聚合放不下落了盘；大表 join 的中间结果太大；或者会话卡住，临时文件反复写。这几条没有一条有现场证据撑着，【待确认】。

真正能回答这个问题的，是第三步抓到的那条 SQL 和它的执行计划。CN 上的 pid、用户名、完整语句，目前都还没拿到，【需补充】。

| 项               | 状态         |
| --------------- | ---------- |
| 最大文件归属 pid 4465 | 确认，来自截图文件名 |
| 5.5T 总量         | 现场给出，未独立复核 |
| CN 节点与 CN pid   | 【需补充】      |
| 执行用户与数据库        | 【需补充】      |
| 触发 SQL 及执行计划    | 【需补充】      |
| 根因属于哪一类         | 【待确认】      |
| 是否已止血、空间是否回收    | 【需补充】      |

把推测写成结论，是这类复盘最容易犯的错。单看一个 1.4T 的文件，证明不了 work_mem 不够，也证明不了是 hash 溢出。同一个现象背后可以是好几种原因，得靠会话和 SQL 去分。

## 六、真碰上了按这个顺序走

- 先把目录清单、文件大小、时间点截屏留证，别先动手删
- 按文件名抠出最大文件对应的 pid，确认是不是集中在单个进程
- 空间充足就走定位：DN 日志 → CN 会话 → 用户和 SQL → 终止会话
- 空间告急就先移走最大文件止血，再走定位，工单里写清楚顺序
- 终止前看一眼会话在跑什么，事务回滚的代价有时候比多占一小时磁盘还高
- 终止后回 DN 复核临时文件是否停止增长、空间是否回收
- 临时文件没自动清掉的，确认无会话占用后再手工处理

## 七、几个容易翻车的地方

- DN 的 pid 和 CN 的 pid 不是一回事，拿 4465 直接去 CN 上查，大概率查不到
- `rm` 正在被写的文件不释放空间，句柄还在
- 会话一杀，事务回滚，写的那部分数据得重跑。杀之前先确认不是关键任务
- 杀之前把 `pg_stat_cluster_activity` 里那一行完整截下来。会话终止后就查不回来了
- 一个 pid 下的多个 tmp 文件是同一件事，不要拆成多个故障重复排查

## 八、哪些字段得换掉

现场信息里有几样不能带进公开文章，整理时统一占位：

| 原始字段        | 文中写法                       |
| ----------- | -------------------------- |
| DN 主节点地址与端口 | `<dn-ip>:<端口>`             |
| 会话标识（长数字）   | `<session-id>`             |
| 日志目录与临时目录路径 | `<DN日志目录>`、`<pgsql_tmp目录>` |
| CN 侧进程号     | `<cn-pid>`                 |

节点编号 DN053、进程号 4465、文件大小和时间都留着。4465 是这次定位的起点，删掉它这篇就没法看了。时间也不能省——03:01 到 08:16 这五个多小时，比一句"持续增长"有用得多。

## 九、和前面几篇接得上

之前聊单机 PostgreSQL 的会话排查，走的就是 `pg_stat_activity` 这条线：先看谁在跑，再看在跑什么，最后决定动谁。这次换成分布式的 `pg_stat_cluster_activity`，中间多了一步 DN 日志对 CN，思路还是那套。

区别在代价。单机上杀错一个会话，影响一个库；分布式里杀错一个 CN 会话，后面挂着一片 DN 的写入。

翻一下自己手上的集群，看看 pgsql_tmp 里有没有躺了几天的大文件。你们那边遇到 tmp 暴涨，是先删还是先查，留言区聊聊。
