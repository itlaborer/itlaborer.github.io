## 三、最关键的一处修复：水位起点

这是本次唯一一处会**静默丢数据**的缺陷，值得把推理链摊开讲。

原来的顺序是：全量搬完 → 取水位列当前最大值 → 以它为起点开始增量。问题在于，如果一行在全量搬运期间被更新，它的新时间戳会小于全量结束时取到的那个最大值；增量阶段按「大于水位」扫描，这行就永远扫不到，目标库安静地少了一次更新。

```text
旧：全量开始 ── 某行被更新 ── 全量结束取 max ── 增量从 max 之后扫
                    ↑ 这次更新落在 max 之前，再也扫不到

新：取起点 ── 全量开始 ── 某行被更新 ── 全量结束 ── 增量从起点扫
        ↑ 全量期间的变化都大于起点，第一轮增量补上，重复行交给覆盖写
```

新版把记录起点的动作提到建表和搬数据之前，逐表打印「增量起点」，并写进断点文件。源码注释把上面这条推理链写得很直白——不是顺手优化，是按数据正确性改的。

顺带，日志增量那边也从「只在提交事件推进位点」升级成了**事务整体落库**：一个事务的行事件先攒着，收到提交事件才在目标库开事务、按表批量写、提交；任一步失败回滚，未提交的事务直接丢弃、位点停在上一个提交点，重启后重放。语义是至少一次，靠覆盖写保证幂等。位点失效时也会明确提示「日志已清理，请重做全量」，而不是闷头重连。

## 四、三条提速路径

### 4.1 单表终于能拆了

上回说加大并行度对一张超大表没用，因为并行是按表分配的。新版加了 `--shards`：先查主键最小值与最大值，把区间均分成最多 N 段闭区间，各片并发搬。

- 只对**单列整数主键**生效，其它表自动退回整表搬运。
- 区间计算用更宽的整数类型，避免整段主键做减法时溢出。
- 与续搬、覆盖写互斥，这两种场景始终走单连接。
- 可与过滤条件叠加，分片条件和原条件取交集。
- 总连接数约为「并行表数 × 分片数 × 2」，别一上来就把源库连接池打满。

⚠️ PG 源各片共享同一个导出快照，跨片时点一致；**MySQL 源各片各开一致性事务，跨片时点可能不同**，源码会直接打告警，需要严格一致就别用分片。

### 4.2 同方言搬运不再逐行转换

PG 到 PG 且开了批量装载、又没有过滤和续搬时，新版把源端的输出字节流直接灌进目标端的输入流，中间不做文本解析和参数绑定。目标端整表一个事务，中途失败回滚，不留半张表。条件不满足时自动退回普通路径，不用手工判断。

### 4.3 写入侧的两处收敛

预处理语句按 SQL 缓存复用，同一张表反复批量写不再重复准备；每条插入语句的行数按「占位符上限除以列数」动态切分，宽表不会撑爆参数上限。这两个改动不显眼，但对大宽表是实打实的稳定性修复。

## 五、结构侧的补强

整库搬迁最容易漏的从来不是数据，是表以外的对象。

- **视图与序列**：同方言条件下随整库迁移，PG 独立序列连当前位点一起重建，避免目标重复发出源已分配过的值；跨方言会明确打印跳过，不假装成功。视图互相依赖时按「每轮剔除成功的、直到一轮没有进展」多轮重试。
- **列级对齐**：目标表已存在时，除了补缺失列和索引，还会比对已有列的类型与非空，先打印差异；加 `--sync-schema` 才真正改。类型名会先归一化，避免同义写法误报；枚举等自定义类型不自动转换，明确提示人工处理。改列前会先删掉依赖它的视图，搬完再按源定义重建。
- **外键降级**：存量脏数据导致外键建不上时，PG 改建成不校验存量数据的形式，MySQL 会话级临时关掉检查再建，都会打印提示。整库迁移不再因为几行脏数据中断，但事后必须补校验或清洗，工具只是把「中断」换成了「带标记的欠账」。

这里也有一个源码与文档的细小分歧：文档说生成列「目标库按同一表达式重算」，但源码在 MySQL 目标是逐列提示「表达式为源方言，不会重建」。跨方言时以源码提示为准。

## 六、给托管实例留的一条路

云上实例通常不允许读本地文件，服务端导入导出的那条路直接被封死。新版加了一条纯客户端通道：导出用客户端接收查询结果的字节流，导入用普通批量插入，全程不需要服务端文件权限。

```bash
# 导出：任意查询写成 CSV
pg2mysql --source postgres://app@<托管库>:5432/appdb \
  --export-sql "select id,name,email from users where created_at >= '2025-01-01'" \
  --export-csv /var/tmp/users.csv

# 导入：按表头列名匹配目标表
pg2mysql --target mysql://app@<托管库>:3306/appdb \
  --import-csv /var/tmp/users.csv --import-table users \
  --batch-size 5000 --truncate
```

要点比命令本身重要：

- 这是**独立模式**：不建表、不整库搬运，导出只需源连接串，导入只需目标连接串；两者同时给出时先导出再导入。
- CSV 约定与 PG 的 CSV 模式一致：**空字段是 NULL，空字符串要写成带引号的空串**。含逗号、双引号、换行的字段按标准转义，读取是流式的，不会把整表读进内存。
- 按表头列名匹配目标列，缺的列走目标默认值或自增，多出来的列提示忽略；字段数对不上会报出具体记录号。
- ⚠️ PG 布尔列经此通道导出是 `t` / `f`，跨方言导入要在查询里显式转换；二进制列按文本处理，只建议用于文本类数据。

## 七、工程化：从「我本地跑过」到「每次提交都跑」

新增的持续集成分三个任务：格式与静态检查、单元测试、集成测试。最后一个用数据库服务容器真跑四种迁移方向的往返，造的数据里特意带了数组、NULL、制表符和换行这些最容易在文本中转里出问题的字符；CSV 往返也有独立用例。本地没配数据库时集成用例自动跳过，不影响前两个任务。

对运维的意义很直接：上一版我只能说「静态读代码，未编译未连库」，现在至少类型映射、建表语句生成、CSV 解析有 34 个单测兜底，四方向有容器内实测。**但吞吐、大表耗时、与定制内核的兼容性，仍然不在这些用例的覆盖范围内。**

## 八、仍然要自己兜住的部分

| 项 | 定性 |
|---|---|
| 过滤条件仍是原始语句内联 | ✅ 源码实证，只拼可信输入 |
| 日志实例编号仍取进程号 | ✅ 源码实证，多实例并发建议错开 |
| 严格一致性：MySQL 并行/分片跨表跨片时点可能不同 | ✅ 源码告警，用单并行或日志增量追平 |
| 未启用传输加密遇强制加密服务端 | 【需补充】未实测 |
| 轮询增量抓不到删除、PG 源无逻辑复制 | ✅ 文档列为已知限制 |
| 生成列跨方言不重建、自定义类型列变更需人工 | ✅ 源码提示 |
| 实际吞吐、分片加速比、定制内核兼容性 | 【需补充】未编译未连库 |

上线前的落地顺序，按新版补两条：预演时留意有没有并行告警；分片前先按连接数公式估一遍源库承载；需要持续增量时，**一次命令里同时给增量开关和断点路径**，让水位或日志位点在搬数据之前落盘；收尾看警告计数、列差异计数和行数校验，外键降级留下的欠账要人工补。

## 九、和上一篇的呼应

中间模型撑起四种方向这个判断，升级后依然成立；这次补的都是模型外围的执行细节与工程约束。工具路线与数据库原生路线（逻辑复制、定制格式导出、外部表）的取舍也没变：工具胜在跨方言、两端不必装扩展、可断点，原生胜在不丢语义。

选型时还是按那三点切：两端是否同构、是否需要持续增量、能否接受建表变更不同步。变化在于，如果是托管实例，现在多了一条「导出 CSV 再导入」的兜底路径，不必再为文件权限去申请白名单。
