# 恢复报错只剩六行目录：一次 pg_restore 复盘

## 一、六行报错里没有一个字是病因

> 一句话结论：命令里的大小写把真正的错误信息筛掉了，屏幕上这六行只是目录。

逐行读完截图又核了一遍官方手册，才确认过滤命令把病因筛掉了。

一台机器上执行恢复，日志里用 `grep Error` 过滤，得到 1 行汇总提示和 6 条 TOC 条目报错。红框圈住其中两条，都与 `uuid-ossp` 扩展有关。

服务端的错误信息以全大写 `ERROR:` 开头。`Error` 只匹配首字母大写的写法，这两类行大小写不同，真正的病因在那条命令里被丢掉了。

这次只做了截图解读与官方口径核对，没有连现场库，也没有看到原始日志全文。六行里连一个失败原因都没有，第一眼却很容易当成六处故障。

## 二、六条报错逐行对账

| TOC 条目 | 系统表 OID / 对象 OID | 对象 | 归属角色 |
|---|---|---|---|
| 36 | 2615 / 17002 | `SCHEMA <schema-a>` | `<owner-a>` |
| 59 | 2615 / 16457 | `SCHEMA <schema-b>` | `<owner-a>` |
| 13 | 3079 / 18242 | `EXTENSION uuid-ossp` | 无 |
| 0 | 0 0 | `COMMENT EXTENSION "uuid-ossp"` | 无 |
| 12444 | 1255 / 10097 | `FUNCTION f_gettable_ddl(varchar, varchar, text)` | `<owner-b>` |
| 12457 | 1255 / 18258 | `FUNCTION sys_guid()` | `<owner-b>` |

`2615` 是 `pg_namespace`，`3079` 是 `pg_extension`，`1255` 是 `pg_proc`。截图里的主机名、日志名、库名、角色名与组件 schema 名都已占位。

条目 0 那行的两个数字都是 0，说明它没有独立 OID，容易被当成另一处故障。

## 三、红框里的两条算一个问题

`EXTENSION uuid-ossp` 是父对象，`COMMENT EXTENSION "uuid-ossp"` 是挂在它上面的注释。父对象没建成，注释必然跟着失败。

条目 0 不需要单独处理。扩展建好之后，注释会在恢复时自动带上。

## 四、大小写把什么筛掉了

```bash
# 现场执行的写法
grep Error <logfile>

# 服务端返回的形态
ERROR:  extension "uuid-ossp" is not available
ERROR:  role "<owner-b>" does not exist
```

| 行类型 | 文本形态 | `grep Error` 是否命中 |
|---|---|---|
| 服务端错误 | `ERROR: ...` 全大写 | 否 |
| 客户端摘要 | `Error from TOC entry ...` | 是 |
| 汇总提示 | `Error while PROCESSING TOC` | 是 |

`ERROR` 四个字母全大写，`Error` 只有首字母大写。大小写敏感的过滤留下的是 `pg_restore` 自己打印的摘要，病因行一条都没进来。

条目号、系统表 OID、对象名都在，失败原因一个字没有。

## 五、恢复工具默认不会停

`pg_restore` 遇到 SQL 错误默认继续，只在结束时显示错误计数。加 `-e` 或 `--exit-on-error` 才会在第一个错误处退出。

| 参数 | 行为 |
|---|---|
| 默认 | 遇错继续，末尾显示错误计数 |
| `-e` / `--exit-on-error` | 第一个 SQL 错误就退出 |
| `-l` | 导出归档的 TOC 清单 |
| `-L` | 只重放清单里保留的条目，顺序按清单 |
| `--no-owner` | 不恢复对象归属，绕开角色缺失 |

这 6 条不代表只错了 6 处，也不代表恢复已经终止。末尾的错误计数才是当次的总数。

```bash
pg_restore -l <dump> > toc.list
pg_restore -L toc.list -e -d <db> <dump>
```

用分号注释掉清单里的无关行，就能只补失败的几条，不必整库重来。

## 六、四个还没定的假设

| 假设 | 依据 | 验证动作 |
|---|---|---|
| A 目标库缺角色 | 4 条带归属角色的报错分成 2 组，角色缺失会让 `ALTER OWNER` 连环失败 | 查 `pg_roles` 里这两个角色是否存在 |
| B 扩展依赖链 | Oracle 兼容的 `sys_guid()` 常见实现依赖 `uuid_generate_v4()`，扩展没建成函数就建不上 | 看函数定义或查 `pg_get_functiondef()` |
| C SCHEMA 已存在 | 其中一个是 `pg_hint_plan` 相关组件，目标库可能自带 | 看原始日志里的 `ERROR:` 原文 |
| D 函数体引用缺失 | `f_gettable_ddl()` 可能引用了尚未恢复的对象，或依赖的语言没装 | 同上 |

四条都是推断，排序只按截图里的分组特征粗分。判据还在原始日志的 `ERROR:` 行里。

A 成立时补角色或加 `--no-owner` 就够，扩展本身没问题。B 成立得先把扩展建上，再重放函数。看不清病因就执行一条 `CREATE EXTENSION`，两种情况下都可能让错误计数继续往上走。

一篇被广泛转载的 PG 兼容实践里，`sys_guid()` 的写法就是先 `CREATE EXTENSION "uuid-ossp"`，函数体用 `SELECT uuid_generate_v4()`。现场函数体是否这样写，需要确认。

⚠️ 六行摘要里没有失败原因，拿它定根因，改库的方向可能一开始就选错。

## 七、这次不能省掉扩展

社区版 PG 13 起内核自带 `gen_random_uuid()`，生成随机 UUID 可以不装扩展。PG 18 又补了 `uuidv7()`。

现场是分布式定制内核，转储里明确列了 `EXTENSION uuid-ossp`，还有一个 Oracle 兼容的 `sys_guid()`。前面那条社区版结论套不过来。

`uuid-ossp` 的 control 文件在 PG 13 与 PG 18 上都标着 `trusted = true` 和 `relocatable = true`。有库级 CREATE 权限就能装，不必给超级用户。

扩展装到哪个 schema，函数就建在哪；那个 schema 不在 `search_path` 里，调用时就会报函数不存在。这与之前那篇《装完 pg_trgm 却说函数不存在》是同一个机制。

TBase 具体版本、CN 上执行 `CREATE EXTENSION` 会不会下发到各 DN，这两处【需补充】。

## 八、先把病因捞回来

先固定证据再动库。同一份日志重跑一次，行号和末尾的错误计数都会变，后面就没法对账了。

```bash
grep -n -i -E "error|fatal|hint|detail" <logfile> | head -80
grep -n -B3 -A3 "uuid-ossp" <logfile>
pg_restore --version
```

`-i` 忽略大小写，`-B3 -A3` 带上前后 3 行上下文。`head -80` 别省，错误行常被挤在几十行上下文里。截图里 `[archiver (db)]` 这种错误前缀看上去属于较早版本或定制内核的输出，社区版 PG 12 之后常见的是 `pg_restore: error:`，用 `--version` 确认客户端版本再下判断。

```sql
SELECT current_setting('server_version');
SELECT name, default_version, installed_version
  FROM pg_available_extensions WHERE name = 'uuid-ossp';
SELECT * FROM pg_extension;
SELECT rolname FROM pg_roles WHERE rolname IN ('<owner-a>', '<owner-b>');
SHOW search_path;
```

先查文件再查权限，最后才动恢复参数：

- 服务端缺 contrib 包，装对应大版本的包，报错形态是找不到 `uuid-ossp.control`
- 只是权限不够，给库级 CREATE 权限，PG 13 起不必给超级用户
- 角色确实缺失，先建角色，或恢复时加 `--no-owner`
- 扩展手工建好之后，用 `-L` 精确重放失败条目

```sql
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";
SELECT sys_guid();
```

恢复完跑一遍 `\dx` 和 `SELECT sys_guid()`，`pg_proc` 里两个函数也顺手对一下。

## 十、把过滤命令换掉

这张截图最麻烦的地方是，六行全都很像病因，其实一行都不是。恢复时带 `-e`，让第一个错误就停下来，日志里自然会有完整的 `ERROR:` 行。

日常翻日志固定用 `grep -n -i -C2 error`。多打 `-i` 和 `-C2` 两个参数，第一次就能看到原因。

翻一下自己最近一次恢复日志，看有没有全大写的 `ERROR:` 被过滤掉。命中的行数发留言区，我想对一下不同环境的报错形态。
