# 一条查询只返回一个分片：分布式库查表大小的透传解法

## 一、结论：一个节点查不出全貌

分布式库查表大小，只连一个节点必然漏数，把查询透传到所有分片、再按子分区表汇总才是完整口径。

> 分布式库的表空间统计，连错节点、漏掉子分区、写死分片名——这三个坑踩中任何一个，查出来的数都不能用。

线上排查磁盘水位时，最容易出现三种"看起来查到了、其实查错了"的症状：

- 在 CN 上执行 `select count(*)`，返回的是全局汇总，你以为看到了分布，其实只看到一个总数。
- 查 `information_schema.tables` 统计表大小，只返回第一个分片的表，其余分片的表根本没进结果集。
- 分区表只查逻辑表名，子分区的物理表全部漏掉，统计值偏小一个数量级。

这三种症状的根子只有一个：**默认情况下，你的 SQL 没有被下发到所有分片。** 解决办法就是 proxy 透传。

## 二、先破误区：默认到底查几个节点

"不写透传是不是只查单节点"——这个问题的答案要分情况，不能一概而论。

| 查询对象 | 不加透传时的实际行为 | 能否看到分布 |
|---|---|---|
| 分布式业务表 | proxy 下发所有分片，**汇总后**返回一个总数 | 否，只见总数 |
| information_schema 元数据表 | 默认只在**单个分片**执行 | 否，只见一个分片 |
| 单表 / noshard | 数据本就只存于第一个分片 | 天然单节点 |
| 广播表 | 每个分片都有全量数据 | 查一个即可 |

关键在第二行。元数据查询不走分片键路由，proxy 默认挑一个分片执行——所以你统计表大小时看到的那一行，只代表分片之一。

加透传注释之后，返回结果会多出一列 `info`，值是分片名。这一列正是我们做分组、看倾斜的依据。

## 三、两套内核，两套透传语法

同一套"透传"需求，在 TDSQL MySQL 版和 TBase / TDSQL PostgreSQL 版里是完全不同的语法，写错一套就跑不通。

| 对比项 | TDSQL MySQL 版 | TBase / TDSQL PostgreSQL 版 |
|---|---|---|
| 透传方式 | `/*sets:xxx*/` 注释透传 | `EXECUTE DIRECT ON (节点名) 'SQL'` |
| 发现分片 | `/*proxy*/show status` | `select * from pgxc_node` |
| 全分片关键字 | `/*sets:allsets*/` | 需按节点逐个透传，或用运维脚本批量 |
| 分片标识列 | 返回值多一列 `info` | 需在 SQL 里自带节点名常量 |
| 表大小函数 | `data_length + index_length + data_free` | `pg_total_relation_size` |
| 碎片空间 | `data_free` | 已含在 total 中，不单列 |

一句话记法：**MySQL 版靠注释，PG 版靠 `EXECUTE DIRECT ON`。**

## 四、TDSQL MySQL 版：先发现分片，再逐分片汇总

### 第一步：拿到分片清单，不要硬编码

```sql
/*proxy*/ show status;
```

返回里重点看四行：`set`（逗号分隔的全部分片）、`<set>:alias`、`<set>:hash_range`、`<set>:ip`。

这一步不能省。巡检里踩过的坑是：**写死分片名的 SQL，扩容后分片名变了，全部报错。** 分片名必须动态发现。

### 第二步：透传所有分片，按子分区表汇总

```sql
/*sets:allsets*/
SELECT  info                                    AS set_name,
        table_schema,
        table_name,
        table_rows,
        ROUND(data_length / 1024 / 1024, 2)                        AS data_mb,
        ROUND(index_length / 1024 / 1024, 2)                       AS index_mb,
        ROUND(data_free / 1024 / 1024, 2)                          AS free_mb,
        ROUND((data_length + index_length + data_free) / 1024 / 1024, 2) AS total_mb
FROM information_schema.tables
WHERE table_schema = '<库名>'
  AND table_name LIKE '<表名>%'
ORDER BY set_name, total_mb DESC;
```

三个要点：

- `/*sets:allsets*/` 是核心，少了它就会退化成单分片查询。
- `LIKE '<表名>%'` 覆盖"逻辑表名 + 分区名"的全部物理子表——这是分区表不漏数的关键。
- `data_free` 是碎片空间，算总空间时别漏了它。

### 第三步：按分片聚合，直接看倾斜

```sql
/*sets:allsets*/
SELECT  info                                     AS set_name,
        COUNT(*)                                 AS sub_table_cnt,
        ROUND(SUM(data_length + index_length + data_free) / 1024 / 1024, 2) AS total_mb
FROM information_schema.tables
WHERE table_schema = '<库名>'
  AND table_name LIKE '<表名>%'
GROUP BY info
ORDER BY total_mb DESC;
```

这一步的输出就是诊断结论：各分片 `total_mb` 相差超过一个数量级，基本可以判定数据倾斜。

### 校验子表是否漏掉

```sql
/*sets:allsets*/
SELECT info AS set_name, table_name
FROM information_schema.tables
WHERE table_schema = '<库名>'
  AND table_name LIKE '<表名>%'
ORDER BY set_name, table_name;
```

先跑这条确认子表确实被覆盖。如果 `LIKE '<表名>%'` 误匹配到相似表名（比如 `<表名>_bak`），用固定中缀收紧：

```sql
AND table_name LIKE '<表名>\_tdsql\_subp\_%' ESCAPE '\'
```

## 五、TBase / PostgreSQL 版：逐节点透传

### 第一步：动态发现 DN 节点

```sql
SELECT node_name, node_host, node_port
FROM pgxc_node
WHERE node_type = 'D'
ORDER BY node_name;
```

### 第二步：逐节点透传查表大小

```sql
EXECUTE DIRECT ON (dn001) 'SELECT ''dn001'' AS dn, pg_size_pretty(pg_total_relation_size(''<模式名>.<表名>'')) AS total_size, pg_total_relation_size(''<模式名>.<表名>'') AS total_bytes';
EXECUTE DIRECT ON (dn002) 'SELECT ''dn002'' AS dn, pg_size_pretty(pg_total_relation_size(''<模式名>.<表名>'')) AS total_size, pg_total_relation_size(''<模式名>.<表名>'') AS total_bytes';
```

注意内部 SQL 的字符串要用**两个单引号**转义，这是 `EXECUTE DIRECT ON` 最容易写错的地方。节点数量按第一步结果增减。

`pg_total_relation_size` 已经包含索引和 toast，不用再额外加 `pg_indexes_size`。

### 分区表：父表与分区合并统计

```sql
EXECUTE DIRECT ON (dn001) '
SELECT n.nspname AS schema_name,
       c.relname AS table_name,
       CASE c.relkind WHEN ''r'' THEN ''普通表'' WHEN ''p'' THEN ''分区父表'' END AS kind,
       pg_size_pretty(pg_total_relation_size(c.oid)) AS total_size,
       pg_total_relation_size(c.oid) AS total_bytes
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind IN (''r'',''p'')
  AND n.nspname NOT IN (''pg_catalog'',''information_schema'',''pg_toast'')
  AND c.relpersistence = ''p''
  AND pg_total_relation_size(c.oid) > 0
  AND c.relname LIKE ''<表名>%''
ORDER BY total_bytes DESC
LIMIT 50';
```

`pg_total_relation_size(c.oid) > 0` 这一条是过滤已卸载的 0 字节空壳表，不加会出来一堆干扰行。

### 批量跑所有节点

```bash
./tbase_run_sql_dn_master.sh "select datname,pg_size_pretty(pg_database_size(oid)) from pg_database"
```

节点少时用 `EXECUTE DIRECT ON` 逐个查，节点多时用这个运维脚本一把梭，两者按现场条件选。

## 六、三个高频坑

| 坑 | 症状 | 规避做法 |
|---|---|---|
| 写死分片名 | 扩容后 SQL 集体报错 | 每次先 `show status` / `pgxc_node` 动态发现 |
| 漏掉子分区表 | 统计值偏小一个数量级 | `LIKE '<表名>%'` 先核对子表清单 |
| 把表空间当磁盘水位 | 数值对不上 `df` 结果 | 表空间 ≠ 物理占用，最终用水位命令核对 |

- ✅ 结论先行：先看各分片 `total_mb` 差异，再决定要不要深入
- ✅ 动态发现分片：扩容、迁移后不返工
- ✅ 分区表按子表汇总：口径完整
- ❌ 只连 CN 查 `information_schema` 就下结论
- ❌ 把 `count(*)` 的全局汇总当成分布数据
- ❌ 拿表空间统计值直接代替磁盘水位

## 七、一页速查

- TDSQL MySQL 版发现分片：`/*proxy*/show status`
- TDSQL MySQL 版全分片透传：`/*sets:allsets*/`
- TBase / PG 版发现节点：`select * from pgxc_node where node_type='D'`
- TBase / PG 版透传：`EXECUTE DIRECT ON (节点名) 'SQL'`
- MySQL 版表大小：`data_length + index_length + data_free`
- PG 版表大小：`pg_total_relation_size`（已含索引 + toast）
- 分区表：先核对子表清单，再 `LIKE '<表名>%'` 汇总
- 磁盘水位：另用系统层命令核对，别拿表空间数代替
